### Почему проект разделён на файлы

Если разместить весь код в `app.py`, файл быстро станет большим и запутанным.
Поэтому у каждой части есть своя ответственность:

- `app.py` запускает приложение;
- `config.py` хранит общие настройки;
- `dashboard.py` формирует стартовую страницу;
- `styles.css` отвечает за оформление;
- `tests/` хранит проверки;
- `docs/` хранит документацию.

Такое разделение называется **разделением ответственности**.

## 6. Точка входа `app.py`

Файл `app.py` — начало выполнения приложения.

```python
from life_os.pages.dashboard import render_dashboard
```

Здесь используется `import`: функция `render_dashboard` импортируется из другого
модуля.

```python
def main() -> None:
```

Объявляется функция `main`.

- `def` создаёт функцию;
- `main` — её имя;
- `()` означает, что функция не принимает аргументы;
- `-> None` — type hint, показывающий, что функция ничего не возвращает.

```python
if __name__ == "__main__":
    main()
```

Этот блок запускает `main()` только при непосредственном запуске `app.py`.
Если файл будет импортирован в тест или другой модуль, приложение автоматически
не запустится.

### Почему импорт Streamlit находится внутри `main`

Так метаданные проекта можно импортировать в простых тестах независимо от
запущенного интерфейса. Позднее мы продолжим отделять интерфейс от логики.

`Path` из стандартного модуля `pathlib` помогает работать с путями независимо

```python
today = date.today().strftime("%d.%m.%Y")
```

```python
columns = st.columns(4)
```

```python
for column, (title, value, caption, color) in zip(columns, cards, strict=True):
```

Здесь:

# Итерация 2. Оболочка интерфейса и навигация

**Дата:** 28 июля 2026 года
**Результат:** пункты бокового меню переключают разделы приложения.

## 1. Цель итерации

На первой итерации названия разделов в боковой панели были обычным текстом.
Они показывали будущую структуру, но на них нельзя было нажать.

Цель второй итерации — создать рабочую навигационную оболочку до подключения
базы данных. Благодаря этому следующие модули можно будет добавлять по одному,
не переписывая точку запуска.

Мы намеренно не добавляли формы, таблицы и демонстрационные показатели.

## 2. Новый модуль `navigation.py`

Навигация вынесена в отдельный файл:

```text
life_os/navigation.py
```

Главные части файла:

- `NavigationItem` описывает один пункт;
- `NAVIGATION_ITEMS` хранит меню;
- `get_navigation_labels()` возвращает названия пунктов;
- `render_navigation()` рисует боковую панель;
- `render_selected_page()` выбирает нужное содержимое;
- `render_module_preview()` показывает единый экран будущего модуля.

### Dataclass

Для описания пункта используется:

```python
@dataclass(frozen=True)
class NavigationItem:
    label: str
    icon: str
    description: str
```

`@dataclass` автоматически создаёт служебные методы класса. Нам не приходится
вручную писать `__init__`.

`frozen=True` делает объект неизменяемым после создания. Это подходит меню:
название и описание пункта не должны случайно изменяться во время работы.

Поля имеют type hints:

- `label: str` — название;
- `icon: str` — символ;
- `description: str` — пояснение.

## 3. Кортеж пунктов меню

Пункты хранятся в кортеже:

```python
NAVIGATION_ITEMS = (
    NavigationItem("Главная", "⌂", "Краткая сводка дня"),
    NavigationItem("Цели", "◇", "Долгосрочные и ближайшие цели"),
)
```

Кортеж похож на список, но предназначен для набора значений, который не нужно
изменять. Это хорошо сочетается с неизменяемым `NavigationItem`.

## 4. Рабочее меню Streamlit

Для выбора раздела используется:

```python
selected_page = st.radio(
    "Основные разделы",
    labels,
    format_func=lambda label: f"{icons[label]}  {label}",
    label_visibility="collapsed",
)
```

`st.radio` возвращает выбранное значение.

`format_func` меняет только способ отображения подписи: перед названием
добавляется значок.

`lambda` — небольшая анонимная функция. Она получает `label` и возвращает
отформатированную строку.

## 5. Callable и передача функции

Функция главной страницы передаётся в навигацию:

```python
render_selected_page(
    selected_page,
    dashboard_renderer=render_dashboard,
)
```

Внутри `render_selected_page` параметр описан так:

```python
dashboard_renderer: Callable[[], None]
```

Это означает: ожидается функция без аргументов, которая ничего не возвращает.

Мы передаём саму функцию `render_dashboard`, без круглых скобок. Если написать
`render_dashboard()`, она выполнится сразу, а не в выбранный момент.

## 6. Почему будущие разделы используют одну заглушку

Мы не создавали десять почти пустых файлов. Все ещё не реализованные разделы
используют `render_module_preview()`.

Преимущества:

- нет дублирования;
- пользователь понимает, что раздел ещё не готов;
- отсутствуют вымышленные рабочие данные;
- дизайн будущих экранов остаётся единым.

Когда начнётся разработка конкретного модуля, его заглушка будет заменена
настоящей функцией страницы.

## 7. Загрузка CSS вынесена из dashboard

Раньше стили загружались внутри `dashboard.py`. Но боковая панель нужна на всех
страницах, поэтому загрузка перенесена в:

```text
life_os/assets/__init__.py
```

Теперь последовательность в `app.py` выглядит так:

```python
load_styles()
selected_page = render_navigation()
render_selected_page(selected_page, dashboard_renderer=render_dashboard)
```

Это читается как краткий сценарий запуска приложения.

## 8. Обработка ошибки CSS

При чтении файла используется:

```python
try:
    styles = STYLES_PATH.read_text(encoding="utf-8")
except OSError as error:
    st.warning(f"Не удалось загрузить оформление: {error}")
```

`try` выполняет потенциально ошибочную операцию.

`except OSError` обрабатывает только ошибки работы с файлом. Ошибка не
скрывается: пользователь видит понятное предупреждение.

Это лучше пустого `except`, который мог бы незаметно спрятать настоящую
проблему.

## 9. Стили выбранного пункта

CSS выделяет активный элемент меню:

```css
label:has(input:checked) {
    background: #f7f1e3;
}
```

Псевдокласс `:has()` выбирает подпись, внутри которой находится отмеченный
переключатель.

Также добавлены:

- экран будущего раздела;
- адаптация значка для узких экранов.

# Итерация 3. Фундамент базы данных

**Дата:** 29 июля 2026 года

**Результат:** схема SQLite создаётся миграцией, а тесты работают с отдельной
временной базой.

## 1. Новые библиотеки

В `requirements.txt` добавлены:

```text
SQLAlchemy>=2.0,<3.0
alembic>=1.14,<2.0
```

SQLAlchemy связывает Python-классы и таблицы базы данных. Такой подход
называется ORM — Object-Relational Mapping.

Alembic хранит последовательность изменений схемы. Каждая миграция описывает,
как обновить базу и как отменить это обновление.

## 2. SQLite

SQLite хранит всю базу в одном локальном файле:

```text
data/life_os.db
```

Для SQLite не требуется отдельный сервер. Файл исключён из Git, поэтому личные
данные не публикуются на GitHub.

## 3. URL базы

В `config.py` формируется адрес:

```python
DATABASE_PATH = DATA_DIR / "life_os.db"
DATABASE_URL = f"sqlite:///{DATABASE_PATH.as_posix()}"
```

SQLAlchemy получает не обычный путь, а URL вида:

```text
sqlite:///C:/путь/data/life_os.db
```

Позднее SQLite URL можно будет заменить на PostgreSQL URL, не меняя модели.

## 4. Базовый класс моделей

В `database/base.py` создан:

```python
class Base(DeclarativeBase):
    pass
```

Все модели наследуются от `Base`. SQLAlchemy собирает информацию об их таблицах
в `Base.metadata`.

## 5. Mixin дат

`TimestampMixin` добавляет общие столбцы:

```python
created_at
updated_at
```

Mixin — класс с повторно используемыми полями или поведением. Он помогает не
копировать одинаковое описание дат в каждую модель.

`server_default=func.current_timestamp()` просит саму базу установить дату при
создании записи.

`onupdate=func.current_timestamp()` обновляет дату при изменении объекта через
SQLAlchemy.

## 6. Модель жизненной сферы

Класс:

```python
class LifeArea(TimestampMixin, Base):
    __tablename__ = "life_areas"
```

соответствует таблице `life_areas`.

Запись:

```python
id: Mapped[int] = mapped_column(Integer, primary_key=True)
```

означает:

- `Mapped[int]` — Python-значение является целым числом;
- `Integer` — тип столбца базы;
- `primary_key=True` — уникальный первичный ключ.

## 7. Ограничения данных

Пример:

```python
CheckConstraint(
    "current_score BETWEEN 1 AND 10",
    name="ck_life_areas_current_score",
)
```

Это правило действует внутри SQLite. Даже если будущая форма пропустит значение
`11`, база отклонит запись.

Реализованы ограничения:

- приоритет от 1 до 5;
- оценки от 1 до 10;
- прогресс цели от 0 до 100;
- дата завершения не раньше даты начала;
- название сферы уникально.

## 8. Перечисления

Статусы и горизонты описаны через `StrEnum`:

```python
class GoalStatus(StrEnum):
    PLANNED = "planned"
    ACTIVE = "active"
    COMPLETED = "completed"
```

Перечисление ограничивает набор допустимых значений и предотвращает опечатки
вроде `"actve"`.

В базе создаётся соответствующее `CHECK`-ограничение.

## 9. Связь один-ко-многим

Связь:

```text
life_areas 1 ─── N goals
```

Одна сфера может иметь несколько целей. Каждая цель относится к одной сфере.

В таблице `goals` хранится внешний ключ:

```python
ForeignKey("life_areas.id", ondelete="RESTRICT")
```

`RESTRICT` запрещает удалить сферу, пока с ней связаны цели. В интерфейсе вместо
удаления будет использоваться архивирование.

## 10. Relationship

В Python связь доступна с обеих сторон:

```python
area.goals
goal.life_area
```

`relationship(..., back_populates=...)` сообщает SQLAlchemy, что это две стороны
одной связи.

Можно создать сферу и сразу добавить цель:

```python
area.goals.append(goal)
```

SQLAlchemy самостоятельно заполнит `goal.life_area_id`.

## 11. Engine

Engine создаётся функцией:

```python
create_database_engine(database_url)
```

Engine знает:

- к какой базе подключаться;
- какой SQL-диалект использовать;
- как получать соединения.

Engine не является одной пользовательской операцией и не заменяет сессию.

## 12. Внешние ключи SQLite

SQLite требует явно включать их проверку:

```sql
PRAGMA foreign_keys=ON
```

Событие SQLAlchemy выполняет эту команду при каждом новом соединении. Без неё
SQLite могла бы сохранить цель со ссылкой на несуществующую сферу.

## 13. Сессия и транзакция

`session_scope(engine)` используется как контекстный менеджер:

```python
with session_scope(engine) as session:
    session.add(area)
```

Если блок завершился успешно, вызывается `commit`.

Если возникло исключение:

1. выполняется `rollback`;
2. ошибка передаётся вызывающему коду;
3. сессия закрывается.

Так незавершённые изменения не остаются в базе.

## 14. Alembic-миграция

Первая миграция находится в:

```text
migrations/versions/4a10246e89fa_create_life_areas_and_goals.py
```

В ней есть:

- `upgrade()` — создаёт таблицы;
- `downgrade()` — удаляет их в обратном порядке;
- `revision` — уникальный идентификатор миграции;
- `down_revision` — ссылка на предыдущую миграцию.

Первая миграция не имеет предыдущей, поэтому `down_revision = None`.

## 15. Инициализация базы

Команда:

```powershell
python -m life_os.database.init_db
```

выполняет Alembic `upgrade head`.

`head` означает последнюю доступную миграцию.

В базе появляется служебная таблица `alembic_version`. Она хранит номер уже
применённой миграции.

Повторный запуск безопасен: Alembic увидит, что база уже обновлена.

## 16. Почему не используется `create_all`

SQLAlchemy умеет создавать таблицы через `Base.metadata.create_all()`, но эта
операция не ведёт историю изменений.

Если одновременно использовать `create_all` и Alembic, появятся два источника
правды. Поэтому пользовательские и тестовые базы создаются миграциями.

## 17. Изоляция тестов

Фикстура pytest получает `tmp_path`:

```python
def database_url(tmp_path: Path) -> str:
    return f"sqlite:///{(tmp_path / 'test_life_os.db').as_posix()}"
```

`tmp_path` — отдельный временный каталог конкретного тестового запуска.

Тесты не обращаются к `data/life_os.db`. После тестов временные файлы могут быть
удалены pytest.

2. Цель сохраняется вместе с существующей сферой.
3. Оценка `11` отклоняется ограничением SQLite.

```text
6 passed
```
